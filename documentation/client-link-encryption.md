# Client-link encryption and rotation

The backend requires `CLIENT_LINK_KEY_ID` and `CLIENT_LINK_ENCRYPTION_SECRET` at startup. Generate a separate random 32-byte secret encoded as base64 (`node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`) and store it in the deployment secret manager. Never reuse JWT or file-access secrets. All backend replicas need the same configuration. Missing or malformed configuration prevents ClientPortalService construction and application startup.

New encrypted copies use `v1.<key-id>.<iv>.<tag>.<ciphertext>` with HKDF-SHA256 (fixed application salt and purpose info), AES-256-GCM, random 12-byte IVs, and authenticated version/key ID. The current ID is 1–32 letters, digits, underscores or hyphens. Optional `CLIENT_LINK_PREVIOUS_KEYS` is a JSON object mapping old IDs to their original base64 secrets; these keys decrypt only. Do not assign a different secret to an existing ID. Envelopes fit the existing VARCHAR(255) token_enc column for the current 32-character tokens; no schema change is needed.

## First deployment: preserve existing active links

1. Back up the database and inventory active rows, including rows with NULL token_enc. Keep the old deployment's actual JWT secret securely until migration is verified. Before deploying, explicitly derive the old **raw AES key** using SHA256 of the UTF-8 string `client-links:` followed by that historical secret. Encode the resulting 32 bytes as base64 and supply it as `CLIENT_LINK_LEGACY_KEY`. Use a secure offline operator process; do not print keys in application logs or commit them. The application never reads JWT_SECRET for encryption or guesses any historical default. If the historical deployment used a default, treat those links as compromised: revoke and replace them instead of preserving them.
2. Configure the new dedicated current secret and ID and the explicit legacy read key on every new instance. Quiesce old writers and deploy all instances together: old application versions cannot read new envelopes. Keep the dedicated secret present even during migration. Do not roll back to the old binary after new writes without a coordinated database restore and recovery plan for links issued since the backup.
3. From `backend`, run `npm run build`, then `node --env-file=.env scripts/rotate-client-link-keys.cjs` for a dry run. It scans **all active links** in batches, verifies decrypted tokens against token_hash, and reports counts only. Run `node --env-file=.env scripts/rotate-client-link-keys.cjs --apply` to re-encrypt available copies under the current key. It preserves tokens, hashes, expiry, revocation, and external URLs. Conditional updates avoid overwriting concurrently changed ciphertext. Nonzero unavailable/concurrent counts produce a failing exit code; resolve and rerun. The operation is resumable and safe to repeat. No production migration runs automatically on startup or link listing.
4. Verify staff redisplay, signed-in client home, and handover URLs on representative existing links. Re-run the dry run with the legacy read key removed **from the command environment** (including inherited variables). Only retire that key from services when all active rows are readable without it and no old writers remain. A dry run with the key still present does not prove retirement is safe.

## Subsequent rotation

Preload the next ID/secret into the read keyrings of all instances before switching any writer. Then switch CLIENT_LINK_KEY_ID/CLIENT_LINK_ENCRYPTION_SECRET to the new pair, retaining the old pair in CLIENT_LINK_PREVIOUS_KEYS (remove the new ID from that object's entries on switched instances). This lets both generations read each other's writes during rollout. Run the same dry run and apply command after all writers switch. Verify again with retired keys absent; remove old read keys only when no active row requires them. Retain keys securely as long as historical backups must be recoverable, or explicitly accept that their encrypted copies will no longer be redisplayable.

## Unrecoverable copies

Public URLs continue to validate using unchanged SHA256 token hashes even if an encrypted copy cannot be recovered. Staff listing/revocation remains available; `redisplay_status: unavailable` and a null URL identify active links whose copies are missing, corrupt, or encrypted under an unavailable key. Restore the correct read key or revoke and issue a replacement through existing staff controls. Never silently replace a token or invalidate its old URL during encryption migration. NULL copies cannot be reconstructed from hashes. Client-home listings omit unavailable copies, and handover redisplay returns a null client_url; already delivered URLs still work until revoked or expired.
