Command Center gate engine
==========================

Evidence-source update: catalogue items with confirmed native tables now resolve through `NativeEvidenceService`; they no longer require duplicate uploads. See `COMMAND_CENTER_EVIDENCE_SOURCES.md` for the complete 83-item mapping and lifecycle rules (16 native entries, 67 upload/drawing entries). This supersedes upload-only descriptions below for native entries. Source resolution requires no additional DDL and does not change historical gate clearances. Command Center shows native source status and links to the record/module; its upload endpoint rejects native requirements. Missing, draft, or rejected native records cannot be bypassed with an uploaded copy. Payment checks use the latest active/completed schedule. Focused source/evidence/transition tests cover this behavior; live MySQL validation remains outstanding.

Existing project phases (updated after reviewing the supplied 39-row dump): all supplied rows belong to CONSULTANCY, with repeated phase codes and numbers. The physical table has no unique constraint on `(module, phase_code)` or `(module, phase_number)`. The migration preserves those rows and their IDs/references without deduplication or renumbering. Each DOCUMENTS phase is inserted with `SELECT ... WHERE NOT EXISTS` scoped to module and phase code, so an existing phase with a different ID is reused without changing its metadata. Existing soft-deleted DOCUMENTS phases are also preserved; review and restore them explicitly if needed. No global unique indexes are added, since the supplied consultancy data would violate them. Run with a single migration runner. Only the phase seed portion is repeatable; the full migration still contains a one-time ALTER.

Phase seed verification used the actual 39 supplied rows in an in-memory SQLite harness executing the seed SELECT/NOT EXISTS statements: all original rows stayed identical, the total became 50 after adding 11 DOCUMENTS phases, a second seed run kept 50 rows, and an existing custom phase ID/title/soft-deletion state was preserved. This verifies seed behavior, not MySQL DDL compatibility or a live migration.

Apply `20260912_command_center_gate_engine.sql` once to a backed-up MySQL 5.7 database containing the supplied schema and the 83 document types. The ALTER is intentionally a one-time migration. The script preserves project evidence and existing gate clearances. It adds missing condition/history tables, an explicit gate-to-document-phase mapping, DOCUMENTS phase records, twelve gate definitions, and catalogue-driven conditions. Existing custom conditions remain in place and must be reviewed for duplicate or obsolete requirements before rollout.

Assign `gates:read`, `gates:clear`, `gates:reopen`, `gates:override`, and `documents:approve` using existing role-permission management. No role receives new privileges automatically. Authentication now resolves these grants from the existing RBAC tables on each request. Overrides additionally require `allows_override` on the gate and a nonblank reason; seeded gates prohibit overrides.

The twelve-gate order comes from the existing engine; the attached master table supplies phase, document, payment, and handoff requirements. The PDF does not define numeric progress thresholds, so newly seeded gates have zero checkpoints except terminal completion (100). Existing checkpoints are preserved. Configure payment milestone codes `TOKEN` and `PHASE_01` to match payment schedules before use.

Command Center uses the DOCUMENTS phase vocabulary, independent of consultancy and PMC planner vocabularies. Phase approval clears the first uncleared gate for that phase through the engine. Phase detail includes all mapped gates; use `GET /projects/:projectId/gates/:gateCode` for individual evidence checklists. Existing clear, reopen, and manual-tick endpoints remain available. A phase without a gate completes on its required evidence; a phase with multiple gates retains the first outstanding gate. Parallel vendor and procurement records do not move the main project's current phase.

Required catalogue records are evaluated even when no project requirement row exists. Conditional records become mandatory when enabled on a project requirement; OPTIONAL records do not block. The planning gate additionally requires an approved contract OR agreement. Review project-specific scope before activation, especially conditional drawings and consultancy-only projects.

Document checks use the latest submission by creation time and ID, so an old approval cannot mask a newer rejected or pending submission. Catalogue items requiring approval need approval; other required documents need submission. Drawings use the drawings table and require all nonsuperseded sheets to satisfy the review rule. Command Center rejects drawing uploads through the document endpoint; use the existing drawings upload flow. Completion flags are display caches, not approval evidence.

Phase conditions also require every configured mandatory DOCUMENTS task/QC definition to have a DONE execution. The migration does not invent the 92 process steps as executable task definitions: populate those through the existing task-definition table when step-level tracking is needed. Catalogue QC sign-off documents remain required. This engine governs gate clearance; it does not add guards to every procurement, quotation, or site-work endpoint. Daily-report frequency, quantities of staged deliveries, and approval per contractor trade need operational rules beyond one catalogue-level record.

Gate clear and reopen transactions serialize on the project row and write transition history atomically with gate changes. Reopening relocks downstream gates and resets project progress. External document/task writers do not share this project lock, so database concurrency verification is still required before production rollout. Evidence changes after clearance require explicit reopening; historical approvals are retained.

Validation: TypeScript no-emit build and focused Jest evidence/transition tests. No live MySQL migration or application startup was performed in this workspace. Test the migration and real uploads, drawing revisions, RBAC grants, concurrent clear/reopen requests, and payment codes in staging before deployment.
