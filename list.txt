## Gate Definition

A gate represents a checkpoint that must pass before workflow execution can continue.

It should conceptually support:

```text
GateDefinition
    id
    name
    mode
    checks
```

Modes should support at minimum:

```text
ALL
ANY
```

A check should support concepts such as:

```text
path
operator
expected value
```

Reuse the existing Condition Engine and operators wherever possible.

Do NOT create a second condition evaluation system.

---

# 4. Gate Evaluation

The Gate Engine must produce a structured result.

Conceptually:

```text
PASSED
BLOCKED
ERROR
```

The result should contain enough information for the UI and audit system to explain:

```text
which checks passed
which checks failed
why a check failed
```

Example:

```text
Execution Gate

✓ Contract approved
✓ BOQ approved
✗ Contractor selected

STATUS: BLOCKED

Reason:
Contractor has not been selected.
```

Do not hardcode construction terminology into the generic Gate Engine.

# 8. GATE RESUME

A blocked gate must be able to resume when relevant business events occur.

The intended architecture is:

```text
Gate BLOCKED
      ↓
Workflow WAITING
      ↓
Relevant Domain Event
      ↓
Event Registry
      ↓
Find affected workflow
      ↓
Re-evaluate Gate
      ↓
PASSED
      ↓
Resume Workflow
```

Do not implement inefficient global polling if the existing event architecture can support event-driven resume.

Do not re-evaluate every waiting workflow for every event.

Use correlation/context information where appropriate.
